THE BENCHMARK EVOLUTION

From one harness to a controlled 3‑SoC experiment

hwbench2 does not throw away hwbench. It preserves the reliability harness, then adds experimental structure so three phones can be compared under the same procedure.

The one-sentence model

V1 establishes the measurement path and failure classification. V2 controls what changes, holds the rest steady, and measures heat soak—not just a fast first run.

03 / UNIFORMITY

Uniform the procedure—not the phones.

The SoC is supposed to change. Everything around it should be controlled, logged, randomized, or acknowledged as a limit.

LOCK 01

Same bytes

Generate input once, copy it, and verify the SHA-256 on every device.

LOCK 02

Same state

Unplugged, battery above 60%, airplane mode, low fixed brightness, apps closed, five-minute idle.

LOCK 03

Same storage

Use internal storage only so documented shared-storage/FUSE variance does not move the result.

LOCK 04

Same engine

One script applies the same timeout, classification, logging, and output checks everywhere.

LOCK 05

Same analysis

One plotter calculates success rate, mean, stdev, throttling curves, temperature, and drain.

Controlled factor

A condition intentionally held constant: input bytes, resolution, device state, storage path, run logic.

Experimental factor

A condition intentionally changed to measure its effect: device/SoC, codec, or software vs hardware encode path.

04 / CONTROLS & VARIABLES

Control the starting line. Measure what changes.

The phones will never be physically identical. The DOE makes that variation interpretable by standardizing the setup, recording the response, and separating deliberate heat soak from unwanted carryover.

PHONE-TO-PHONE ACCOUNTING

Where each variable goes

ELIGIBILITY CONTROL
Starting battery and power state

Begin above 60% and unplugged. This avoids charging heat and low-charge behavior, but it does not make different batteries equivalent; the starting percentage remains part of each run record.

HELD CONSTANT
Background load

Airplane mode on, apps closed, low fixed brightness, and five minutes idle before the first run reduce unrelated CPU, radio, and display work.

MEASURED
Battery response

Battery percent is captured at run start and end, then summed across a cell. Report it as a coarse, device-relative response: percentage points are not equal energy across batteries with different capacity or health.

MEASURED + TREATED
Heat

Skin temperature is logged before and after every run. Cells start near the same baseline, while the sustained block intentionally accumulates heat to expose throttling.

BLOCKED FACTOR
Phone and SoC

Each handset is one experimental block and runs the same recipes. Differences are reported as device-level case-study effects, not generalized to every phone with that SoC.

RANDOMIZED
Residual order effects

shuf changes cell order and records the seed, so one path is not always advantaged by running first on a cooler phone.

HEAT HAS TWO JOBS

Noise between cells. Treatment within a cell.

Reset the baseline

Before the session: five-minute idle. Between cells: wait until the phone returns to baseline + 2°C, capped at ten minutes.

Let the block heat up

The ten sustained runs have no internal cooldown. That rising thermal load is deliberate.

Observe the response

Plot fps and skin temperature by run number. A falling fps curve reveals the throttling knee.

Contain the carryover

Cooldown before the next randomized cell keeps one cell’s heat from becoming the next cell’s starting advantage or penalty.

Two encode paths, one workload

Both paths receive the same source bytes and target resolution. What changes is which compute engine performs the compression.

SOFTWARE / CPU ENCODE

General CPU cores do the work

ffmpeg executes the codec as ordinary ARM instructions: libx264 for H.264 and libx265 for HEVC. Motion search, transforms, quantization, and entropy coding all run in software.

StrengthPortable, mature, and predictable across devices.
CostHigh general-purpose CPU load can mean lower fps, more heat, and more battery use.
HARDWARE / MediaCodec

Dedicated video silicon does the work

ffmpeg asks Android’s MediaCodec API to hand encoding to the SoC’s fixed-function video engine instead of calculating the full codec on the CPU.

INPUTframes
→

PromiseHigher throughput with less CPU work, heat, and battery drain.
RiskMediaCodec support varies: a run can fail, hang, or return success with an empty file.
WHAT THE DOE TESTS

For each phone and codec, compare fps, completion rate, temperature rise, throttling, and battery drop. The harness requires both a successful exit and a non-empty output, so “fast but unreliable” cannot win silently.

Stretch path: hw_dec uses hardware decoding before software encoding. It helps isolate the decode side, but it is not part of the 180-run core design. Also, software CRF versus hardware 8 Mbit/s is a configured-path comparison—not an equal-quality efficiency test.

05 / RUN SEQUENCE

Every stage is a gate.

Do not burn 180 runs to discover a bad sensor or mismatched input at the end. Prove the next layer before scaling up.

06 / INTERPRETATION

Five signals, five questions.

The benchmark does not produce one universal “winner.” It separates throughput, consistency, failure behavior, thermal response, and coarse power response.

SIGNAL 01

Throughput

Which codec/path/device cells finish fastest, and how large is hardware’s advantage over software?

mean fps ± stdev
SIGNAL 02

Reliability

Does a cell consistently finish, produce an empty file, fail, or hit the timeout?

OK / FAIL / TIMEOUT + success %
SIGNAL 03

Throttling

Does fps decay across the ten-run sustained block, and where does the curve bend?

fps vs sustained run #
SIGNAL 04

Thermal response

How does end-of-run skin temperature move as each device heat-soaks?

temperature vs run #
SIGNAL 05

Battery response

Which cells show more battery drop under the same procedure?

summed % drop per cell
INTERPRET WITH CARE

Uniform does not mean perfect equivalence.

The design is disciplined enough to answer the pre-registered case-study questions, but its limits should travel with every chart.

One handset per SoC

This is a three-device case study, not a population estimate for every Exynos, Snapdragon, or Tensor phone.

Different encode targets

The current script uses CRF for software and 8 Mbit/s for hardware. It compares the configured paths, not equal-quality encoding efficiency.

Coarse telemetry

Battery percentage is low-resolution, and CPU MHz is a cross-core snapshot—not a time-average over the whole encode.
